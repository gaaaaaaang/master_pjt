# Text2SQL 추가 일반화 작업 결과

브랜치: `fix/adv_t2s`. 추가 작업 시작 2026-09-08 06:20:40 KST, 종료 2026-09-08 07:51:09 KST.

메타를 보고 계획하는 경로에서 발견한 오류를 수정했고, 실제 채팅 화면에서 조회·최종 답변까지 확인했다. 일반 자연어 질문의 정확도 100%를 보장하는 결과는 아니다.

## 검증 결과

| 평가 | 결과 | 해석 |
|---|---:|---|
| 개발 기준선 | 11/24 | 6건에 LLM TPM 한도 오류 포함 |
| 개발 전체 재평가 | 22/24 | 조회 18/20, negative 4/4; 한도 오류 없음 |
| 최초 별도 검증 | **14/16** | 조회 12/14, negative 2/2; 고정 코드/fixture |
| 발견한 오류 수정 후 개발 회귀 | **5/5** | 시간 기준 3변형과 이미 본 실패 2건 |
| 동일 실패 문항 추가 반복 | **2/2** | 식별자 매칭 수정 후 재실행 |
| 전체 단위·회귀 테스트 | **474개 통과** | 기존 프로젝트 테스트 포함 |
| 기존 실제 DB 회귀 | **79/79** | 읽기 전용 실행 |
| 이번 라운드 저장 SQL 재검증 | **43/43** | 현재 메타·계획 검사·실제 DB 기준 SQL 비교; 새 생성 평가 아님 |

최초 별도 검증의 두 실패는 기간의 시작/종료 열 혼용과 NOT NULL 필터의 계획 누락이었다. 각각 수정 후 443과 2592라는 기준 결과에 일치했다. 최초 14/16은 그대로 보존하며, 사후 회귀를 합쳐 16/16이라고 표기하지 않는다. 자체 작성한 작은 평가 세트이므로 운영 질문 전체에 대한 통계적 정확도 추정도 아니다.

이전 라운드 저장 계획 8개는 7개가 통과했고, 필수 top-N 필드 도입 전 계획 1개는 `result_limit`이 없어 현재 검사에서 거절됐다. 이를 숨기거나 검사를 완화하지 않고 별도로 기록했다.

## 실제 화면 검증

- 화면 문맥 FAB10보다 질문의 FAB13이 우선: `lot_id IS NULL` 행 수 **864**, 최종 답변과 시뮬레이션 출처 확인.
- 같은 대화의 새로운 `equipment_id IS NOT NULL` 질문: **2592**, 이전 lot_id 필터가 새 SQL에 섞이지 않음.
- FAB12 기간 합계: 상위 Planner가 테이블명을 요구하며 막는 문제를 추가 발견. Planner 수정 후 **동일 질문을 추가 힌트 없이** 재실행해 **443**과 interval_end 기준의 최종 답변 확인. 이전 실패 응답이 대화에 남아 있어도 정상 복구.

## 주요 변경

- 공통 메타에 실제 영역 값과 기본 시간 기준을 제공하고, breakdown의 영역 연결과 PM의 장비군 연결을 구별했다.
- 관련성 없는 테이블을 채워 넣지 않고, 필요한 관계 대상은 유지했다. 같은 질문 19개에서 첫 계획 입력 문자 수 중앙값이 33,906→18,823으로 약 44.5% 감소했다. 과금 토큰이나 작업 전체 사용량 수치는 아니다.
- CTE에서 실제 사용 소스·집계 별칭·최신 MAX 계보를 검증하고, 계획 외 필터·집계값 변형·지표 별칭의 역할 바뀜을 차단했다.
- NULL 포함 행 수와 nullable 열 COUNT를 구별하고, 명확한 NULL 조건을 실제 컬럼에 바인딩했다.
- 날짜 범위는 명시된 시작/종료 기준을 존중하고, 기준이 없으면 메타 기본 시간 열을 일관되게 적용한다.
- `equipment_id` 안의 `pm`을 PM 테이블로 오인하지 않도록 식별자 경계를 적용했다.
- Planner v3는 물리 테이블·스키마·데이터 계층 탐색을 Text2SQL에 위임한다. FAB, 지표, 날짜 의미 같은 실제 사용자 모호성은 계속 확인한다.

업무 테이블 78개는 기존 OID 유지·행 수 감소 없음, FAB10~13 장비군 키 중복/NULL 0을 확인했다. 내용 체크섬 검증은 아니다. 이번 추가 작업의 DB 변경은 메타 동기화이며 업무 데이터 삭제·수정은 하지 않았다.

## 남은 한계

- 지표·조인·시간 구간의 업무 의미는 담당자의 SSOT 검토가 필요하다.
- SQL 구조 검증은 임의 SQL의 의미 동치 증명이 아니다. 표현이 복잡하거나 의미가 부족한 질문은 재질문·미지원이 가능하다.
- 실제 사용자 질문을 수집한 더 큰 외부 평가와 반복성 측정이 필요하다. 모델의 confidence 값을 측정된 정확도로 해석하지 않는다.
- 기존 사용자 변경을 보존했으며 커밋·병합·배포는 수행하지 않았다.

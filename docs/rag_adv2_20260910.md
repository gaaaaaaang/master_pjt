## 이전 작업과 연결

이전 세션 `01a07c24-3b25-7af2-884c-d31fb31bebd7`의 RAG 검색 고도화와
[확장 기록](rag_extension_20260908.md)을 확인했다. BM25/dense 후보, RRF,
bounded reranker, 원문 span 인용, 생성 후 근거 검토, 승인·기록 원문 보존을 이어받았다.
이전 세션에서도 PM Engineer 승인 누락 및 모델 검토의 과신이 발견됐다.

## 원인과 변경

1. **검색 후 이슈 필터로 근거 소실:** 기존에는 top-k와 context 예산을 소비한 뒤
   이슈 불일치 후보를 제거했다. `ext_knowledge_update`에서는 검색 trace가 5개인데
   실제 반환 근거는 0개였다. 이슈 필터를 BM25 후보 선정 및 dense 후보 병합 전에
   적용하고 `evidence_count`, `post_filter_dropped_count`를 노출한다.
   명시 playbook ID 조회와 FAB·문서 상태·승인 SOP 필터는 유지한다.
2. **질의 어휘 누락:** 지식 문서·플레이북 업데이트를 KB 업데이트로 인식하고,
   Hold 해제 표현을 보강해 보류·해제 비교에서 양쪽 근거를 확보한다.
3. **답변 범위와 중복:** 역할·의사결정·필드 관계를 질문 순서에 맞게 설명하도록
   생성 지시를 보완했다. 본문에 원문 조건이 그대로 있으면 추가 인용문을 중복하지
   않고, 빠진 승인·기록 원문은 답변 뒤에 표시한다. 번역·의역까지 같다고 추정해
   조건을 제거하지 않으므로 일부 중복은 남는다.
4. **문서 상태와 버전 관리 혼동:** 첫 API 실행에서 `draft/reviewed/approved`를
   버전 관리라고 답하고 모델 검토도 통과시켰다. 버전·개정 이력을 요청했는데 원문에
   해당 표현이 없는 경우 그 주장을 제외하고 나머지는 부분 답변으로 반환한다.
   이 검사는 제한된 한·영 표현의 부재 검사이며, 표현이 있다는 이유만으로 버전
   정책을 검증한 것으로 취급하지 않는다. 의미 정합성은 여전히 모델 검토의 한계가 있다.
5. **검증 실패 시 전체 답변 중단:** 반복 실행의 Hold 문항에서 인용에 없는 숫자가
   생성돼 답변 전체가 거절됐다. 형식·원문·숫자 검증 오류에만 같은 근거로 최대 1회
   수정 기회를 준다. 다시 검증하고 실패하면 보류한다. API 전송 실패는 이 수정
   경로에서 재시도하지 않는다. `generation_attempts`, `validation_errors`를 기록한다.

최종 실행에서 근거를 찾는 7문항은 supported 6개, partial 1개이며, 답변 불가 3개는
모두 insufficient였다. KB 업데이트는 근거가 복구됐지만 실제 문서에 버전 관리 기준이
없으므로 partial이 맞다. 이 응답은 Ragas Relevancy에서 0점을 받았다. 이를 점수 개선을
위해 supported로 바꾸지 않았다. 첫 v5의 더 높은 관련성에는 잘못된 버전 관리 설명도
포함돼 있으므로 첫 실행을 최종 성능으로 선택하지 않는다.

중간 v6에서는 PM의 승인 관계에 대한 검토 모델 오판으로 partial, Hold 비교에서
인용에 없는 숫자 검증 실패로 insufficient가 발생했다. 최종 호출에서는 그 두 문항이
supported였지만, 생성의 변동도 있으므로 모든 차이를 마지막 코드 수정의 효과로
귀속하지 않는다. 최종 실행의 재가동 시간 질문에서 `insufficient`와 claims를 함께
생성한 오류가 발생했고, 1회 수정 후 빈 claims의 정상 insufficient 응답을 확인했다.

최종 Faithfulness는 개선됐고 관련성은 소폭 높아졌으나 **안정적인 관련성 향상은 아직
입증하지 못했다**. 동일 모델 judge, 단일 최종 실행, 기존 개발셋이라는 한계가 있다.
Context Precision은 정답 문서 annotation 없이 답변과 context를 비교하는 지표이며,
1.0을 검색 전반의 완벽한 정확도로 해석하지 않는다. 최종 43개 인용을 반환 원문과
대조해 모두 일치함을 확인했다. 원문 존재 검증과 문장의 의미·역할·조건 검증은 다르다.
최종 소스 SHA256: `2ce1df3c098ea0d65844b82131a046705cdc317cdf57d7bd6e2b08fa4a9e0bba`.

## 검증 범위와 남은 작업

- 최종 RAG 관련 테스트 **146 passed**. 전체 Python **658 passed, 1 failed**.
  실패 `test_graph_requeries_after_old_missing_table_error`는 수정 전 `4ebf833` export에서도
  같은 `queries == 0` 실패를 재현했다. RAG 변경과 무관한 기존 SQL 복구 회귀다.
- 전체 테스트의 AutoSched 원본 데이터는 기존 폴더를 임시 연결해 읽었다.
  원본 데이터나 다른 작업의 소스 변경은 복사하지 않았다.
- 변경 파일 Ruff와 `git diff --check` 통과.
- 실제 평가는 기존 설정의 로컬 검색 + feature reranker + 문서 답변 생성이다.
  Milvus 실제 검색, HTTP/SSE, SQL과 결합한 복합 그래프의 새 성능 수치가 아니다.
- 역할 질문에서 일반 RACI 설명이 추가되는 문제, 의역으로 남는 원문 중복,
  모델 검토가 승인 역할의 관계를 잘못 판단하는 문제는 남아 있다.
- 다음 작업은 질문별 요구사항과 직접 대응하는 claim의 평가, 별도 gold answer/context
  주석, 실제 사용자 질문 holdout, 반복 실행·다른 judge 비교다.
  Milvus 설정을 활성화할 때는 현재 local corpus와 같은 manifest로 별도 비교해야 한다.
- 기존 v2 challenge에서 남은 누락은 챔버 정지 기록, toolgroup 앞 재공 집중,
  소모품 부족, 우회 장비 qualification, 사건 보고 주기, 사건 종료 뒤 새 판단 기준
  추가 질문이다. 단순 키워드 보강만으로 의미 검색을 대체했다고 보지 않는다.

```bash
  /private/tmp/master_pjt_rag_adv2/apps/assistant/scripts/evaluate_rag_quality.py \
  --live --source-root /private/tmp/master_pjt_rag_adv2 --output /tmp/rag-quality.json
```

스크립트는 그 생성·채점 경로를 추출했으며 다른 에이전트 평가 코드는 포함하지 않는다.

# FAB AI Assistant — 테스트 단계 문제 해결 및 기술 리서치

제공된 Talent Lab 과제 양식의 항목과 순서에 맞춘 입력용 문서다. 기존 As-Is → To-Be 문서를 재구성하고, RAG는 2026-09-10 PR #12 병합 후 재평가 기록을 추가 반영했다. 평가 시점·대상이 다른 결과는 구분했으며, 아래 수치는 기존 실행 기록을 인용한 것으로 이번 문서 작성 중 평가를 다시 실행하지 않았다.

## 주요 문제 해결 및 기술 리서치 (테스트 단계)

테스트 과정에서 발견한 핵심 문제는 문서 근거 누락과 답변 조건 누락, SQL의 의미 불일치, 재실행 후 오래된 근거 혼입, 과도한 모델 입력과 수정 호출, 스트림 오류 복구, 시간에 따른 데이터 변화 부족이었다. 각 문제를 검색·계획·검증·상태 관리 단계로 나누어 개선했다.

| 이슈 구분 | 문제 상황 및 원인 | 리서치 및 해결 과정 (Reference & Solution) |
|---|---|---|
| 품질/환각 — RAG | PM 승인·복구 기록 같은 필수 조건이 요약에서 누락되고, 문서 상태를 버전 관리 정책으로 잘못 설명하는 사례 발생 | **검토:** 하이브리드 검색, 원문 단위 grounding, 생성 후 검증과 제한적 Self-Correction. **적용:** 페이지·절차 단위 청크, BM25·dense 후보의 RRF 통합, 원문 span 인용 검증, 승인·기록 조건 보존. 문서에 없는 버전 정책은 제외하고 부분 답변으로 반환. 형식·원문·수치 검증 실패는 동일 근거로 최대 1회 수정 후 재검증 |
| 품질/검색 누락 | top-k 및 근거 예산을 사용한 뒤 이슈 불일치 문서를 제거해, 검색 trace는 5개지만 실제 반환 근거는 0개인 사례 발생 | **검토:** 검색 후보 필터의 적용 순서와 복합 질문 coverage. **적용:** 이슈 필터를 후보 선정·병합 전으로 이동하고, 지식 문서 업데이트·Hold 해제 표현 보완. 실제 반환 근거 수와 필터 제거 수 기록 |
| 품질/SQL 의미 | SQL이 실행돼도 NULL 행 수, 날짜 시작·종료 기준, 조인 중복 집계가 질문 의미와 다를 수 있음 | **리서치:** PANDA 및 MARS/TriSQL의 메타 기반 탐색·계획 아이디어, SQL AST 검증. **적용:** 공통 메타 검색 → 구조화된 의미 계획 → 계획 검증 → SQL 생성 → SQLGlot AST 대조 → 읽기 전용 실행. 논문의 전체 학습 절차를 재현한 구현은 아님 |
| 품질/실행 제어 | Agent 성공이 질문 충족을 보장하지 않고, SQL 재조회 후 이전 검색·차트가 최종 답변에 섞일 수 있음 | **검토:** 단계별 입력·성공 기준, 제한된 복구, 현재 유효 결과와 이력 분리. **적용:** Planner에 답변 요건·의존성 명시, Supervisor가 성공·실패 결과 모두 검토, `active_results` 관리와 종속 결과 무효화·재계산 |
| 속도/비용 | 관련 없는 스키마 설명이 모델 입력을 늘리고, 답변 형식 오류와 불필요한 배경 설명이 추가 수정 호출을 유발 | **검토:** schema retrieval, 제한된 생성·재시도, sampling·프롬프트 범위 조정. **적용:** 관련 테이블 후보 축소, 기존 deterministic fast path 유지, RAG 생성·검토에 temperature=0과 질문 중심 작성 규칙 적용 |
| 보안/가드레일 | 허용되지 않은 SQL, 다른 FAB·기간 조회, 근거 없는 수치·확정 원인, 시뮬레이션을 실측으로 표현하는 응답 위험 | **적용:** 기존 read-only·allowlist 유지, 계획과 실제 SQL 및 반환 근거의 범위 대조, 최종 답변의 값·대상·출처·한계 검증. 조건이 모호하거나 근거가 없으면 확인 질문·부분 답변·보류 상태로 반환 |
| 예외/화면 | SSE가 중간에 끊기거나 재시도 시 변경된 FAB 설정이 적용되고, 새로고침 후 초안·상태가 사라지는 문제 | **검토:** 스트림 완료 판정, 요청 payload 보존, 대화별 UI 상태 복원. **적용:** 실패·취소·수신 중단 구분, 원래 범위·대화 ID를 유지한 재시도, 초안 및 피드백 재시도 상태 복원 |
| 데이터/테스트 현실성 | 고정 보고서·스냅샷만으로는 공장별 특성과 사건의 지속·복구를 시간 흐름에 따라 검증하기 어려움 | **검토:** 상태를 보존하는 이벤트 시뮬레이션. **적용:** FAB별 페르소나를 설정하고 15분마다 raw event 생성·적재. 상태·사건 테이블을 별도로 유지해 `active → recovering → recovered` 연속성 제공 |

리서치·적용 근거: [Text2SQL 설계 및 작업 기록](text2sql_hackathon_20260907.md), [RAG 검색 설계](rag_hackathon_20260907.md), [RAG 후속 개선](rag_adv2_20260910.md), [Planner/Supervisor 개선](planner_supervisor_hackathon_20260908.md).

## 1. LLM 답변 품질 평가 및 개선

### 1-1. RAG 기반 질의응답

| 항목 | 내용 |
|---|---|
| 평가 대상 기능 | 문서 검색, 필수 근거 확보, 원문 기반 답변 생성·인용, 근거 부족 시 부분 답변·보류 |
| 평가 방식 | 기존 확장 fixture 10문항: 답변 가능 7문항·답변 불가 3문항. 동일 fixture·corpus hash, GPT-4.1, text-embedding-3-large, Ragas 0.2.15로 평가. 로컬 검색 + feature reranker + 실제 LLM 생성·검토 경로 사용 |
| 평가 결과 — 개선 전 | 답변 가능 7문항 기준 Faithfulness **0.8286**, Answer Relevancy **0.4425**, Context Precision without reference **0.8571**. 필수 evidence marker 전체 확보 **5/7** |
| 발견한 문제 | KB 업데이트 근거가 검색 후 필터에서 소실. Hold 보류·해제 중 일부 근거 누락. 승인·기록 조건의 누락과 문서 상태/버전 정책 혼동. 형식·수치 검증 실패로 추가 수정 호출 발생 |
| 개선 조치 | 이슈 필터를 후보 선정 전으로 이동, 질의 표현 보완, 질문의 요구사항에 맞춘 생성·검토 지시, 원문 승인·기록 조건 보존, 없는 정책에 대한 부분 답변, 제한된 수정 후 재검증, RAG temperature=0 명시 |
| 개선 후 결과 | **PR #12 병합 커밋 재평가:** Faithfulness **0.8881**, Answer Relevancy **0.4504**, Context Precision without reference **1.0000**. 필수 evidence marker 전체 확보 **7/7** |
| 답변 상태·인용 검증 | 전체 10문항 중 supported 6개, partial 1개, insufficient 3개. 반환 인용 **32/32**가 검색 원문·문서·페이지와 일치. 생성 API 사용 8문항 모두 첫 생성으로 검증 완료 |
| 남은 한계 | 관련성 상승은 작고 일부 문항 점수는 하락. 기존 개발셋·동일 모델 judge·단일 재평가이며 Milvus/HTTP/SSE/전체 graph 평가가 아님. 인용 일치는 의미적 타당성 100%를 뜻하지 않음 |

전체 10문항 평균은 Faithfulness **0.6467 → 0.6550**, Answer Relevancy **0.3098 → 0.3153**, Context Precision without reference **0.6000 → 0.8000**이다. 정상적으로 보류한 답변도 생성 평가에서 낮은 점수를 받을 수 있어, 전체와 답변 가능 부분집합을 함께 기록했다. Context Precision은 정답 context annotation 없는 지표이며 검색 정확도 100%로 해석하지 않는다.

**As-Is:** 단일 검색 경로 → 상위 청크 전달 → 답변·검토

**To-Be:** 구조 보존 청크 → 범위·이슈 필터 → 검색 순위 통합·재정렬 → 필수 근거 확인 → 원문 기반 생성 → 인용·주장·조건 검증 → 지원/부분/보류 응답

하이브리드 검색은 구현돼 있으나 위 Ragas 수치는 로컬 검색 경로의 결과다. 근거: [PR #12 재평가](pr12_rag_retest_20260910.md).

## 2. 성능 및 비용 최적화

### 2-1. Text2SQL 모델 입력 축소

| 항목 | 내용 |
|---|---|
| 기존 병목 | 질문과 관련 없는 테이블·중복 설명까지 모델에 전달해 계획 입력이 커짐 |
| 개선 전략 | 관련 스키마만 우선 탐색하되 필수 테이블·검증된 관계는 보존 |

### 2-2. RAG 생성·검토의 추가 호출 감소

| 항목 | 내용 |
|---|---|
| 기존 병목 | 없는 수치 질문에서 보류 상태와 주장을 함께 생성해 검증 오류·수정 호출 발생. 불필요한 배경 설명으로 답변과 검토 범위 확대 |
| 개선 전략 | 질문에서 요구사항을 도출하고, 보류 응답 형식을 명확히 하며 생성·검토의 변동 축소 |
| 적용 기술 | RAG 생성·검토 temperature=0, 질문·역할 중심의 간결한 작성 지시, 원문 조건 보존, 보류 시 빈 claims 계약, 제한된 수정 호출 |
| 평가 방식 | 같은 6문항·같은 검색 근거를 고정해 기준/수정 코드 각각 3회 실행: 전후 각 18회, 총 36회 |
| 개선 결과 | 검증 오류 후 수정 필요 **3/18 → 0/18**, 모델 호출 **36 → 33회**, 평균 생성·검토 시간 **8.73 → 6.16초**, 평균 답변 길이 **805 → 608자** |
| 결과 해석 | 검색·HTTP/SSE를 제외한 생성·검토 측정이며 서버 부하를 통제하지 않음. 시간 감소 전체를 코드 효과로 단정하지 않음. 실제 과금 절감액은 미측정 |
| 남은 병목 | 대체 장비 질문의 답변 길이 변동은 악화. temperature=0만으로 완전한 재현성·의미적 안정성을 보장하지 않음 |

근거: [RAG 안정성 실험](rag_stability_20260910.md).

### 2-3. 전체 실행의 호출·시간 관리

| 항목 | 내용 |
|---|---|
| 개선 전략 | 필요한 Agent만 선택하고, 기존 fast path 및 명시적 재시도 예산으로 불필요한 실행 제한 |
| 적용 기술 | Text2SQL 후보 생성 최대 2회. Supervisor 명시 재시도 Agent당 1회·전체 2회, 재계획 1회, 대체 Agent 1회. RAG 근거 문자 예산·제한형 reranker·취소 후 추가 호출 차단 |
| 측정 결과 | 9월 10일 복합 graph 14문항 평균 **24.70초**, 최대 **53.27초**. PR #12 RAG 단독 재평가 10문항의 검색·생성·내부 검토 평균 **4.84초** |
| 측정 경계 | 두 수치는 서로 다른 실행 범위다. Judge 채점·HTTP 왕복·브라우저·운영 부하를 포함하지 않으며, 동일 조건의 전후 비교가 없어 전체 응답시간 단축률로 사용하지 않음 |

현재 워크플로우는 상위 근거를 후속 Agent가 사용하는 **순차 실행**이다. 양식 예시에 있는 병렬 도구 호출, Redis Semantic Cache, 비용 35% 절감은 이번 구현 성과로 기재하지 않는다.

### 4-1. FAB별 페르소나를 반영한 15분 주기 데이터 적재

| 항목 | 내용 |
|---|---|
| 문제 상황 | 고정 보고서·구간 스냅샷만으로는 서로 다른 FAB의 상황과 사건 발생·지속·복구를 시간에 따라 분석하기 어려움 |
| As-Is | SMT2020 원천·AutoSched 보고서와 FAB별 프로파일을 반영한 스냅샷·상세 이벤트 중심 |

| 확인 범위 | 15분 예약 및 `--interval-minutes 15` 실행 설정, 로컬 생성 코드와 상태·사건 테스트 내용 확인. 최신 DB 적재 시각·누적 행 수·무중단 실행 여부는 본 문서에서 새로 검증하지 않음 |

| FAB | 페르소나와 운영 특징 | 대표 상황·분석 포인트 | raw 초기 WIP / 수율 추세 / 신규 사건 기본 확률 |
|---|---|---|---|
| **FAB10 — 안정 생산형** | `stable_hvlm`. 검증된 공정으로 소수 제품을 많이 생산하는 대량·소품종 공장 | 작은 계측 이상·photo 대기열 증가를 관찰하고 안정 상태와 비교 | **1,260 / 97.3% / 10%** |
| **FAB11 — 노후 설비 관리형** | `aging_lvhm`. 다양한 제품을 소량 생산하며 노후 설비·정비 일정을 관리하는 공장 | PM 초과·장비 다운·carrier 대기, 정비 지연과 복구 상태 분석 | **920 / 95.8% / 22%** |
| **FAB12 — 신규 공정 안정화형** | `new_process_mix`. 신규 공정·제품 조합을 적용하며 레시피와 품질을 안정화하는 공장 | 레시피 튜닝·수율 변화·재작업 증가와 공정 조정 전후 비교 | **1,110 / 96.2% / 25%** |
| **FAB13 — 고부하·증설형** | `high_load_expansion`. 생산 물량이 몰리는 증설 국면에서 WIP와 병목을 관리하는 공장 | WIP 급증·병목·hold·수율 저하, 사건의 지속·복구와 대기시간 분석 | **1,460 / 96.7% / 32%** |

대표 상황은 기존 스냅샷 생성기의 FAB별 사건 설정에 근거한 페르소나 설명이다. 현재 raw 생성기는 공통 사건 후보를 사용하며 FAB별 초기 상태·발생 확률을 다르게 적용한다. 특정 사건을 특정 FAB에만 고정하지 않는다. 확률은 활성 사건이 없을 때의 기본값이며 건전성에 따라 가중한다. 초기값은 합성 설정으로 실제 공장 KPI가 아니다.

**변경 흐름:** 15분 실행 → 직전 구간 결정 → FAB 페르소나·이전 상태 로드 → 정상/신규 사건/진행 사건 판단 → raw event 적재 → 최신 상태·복구 진행 저장 → 다음 회차와 Agent 조회에 사용

전날 raw를 조회용 스냅샷·이벤트로 변환하는 일일 projection은 별도 후처리다. 9월 10일 현재 로컬에 `project_fab_raw_events_daily.py`가 존재하나, 실제 일일 실행 완료 여부는 이번 문서 작업에서 검증하지 않았다. 기존 원천·스냅샷을 유지하며, 합성 데이터를 실제 MES·센서 수집으로 표현하지 않는다.

### 4-4. 전체 통합에서 유지한 계약

**데이터 시뮬레이션 → Text2SQL·RAG의 근거 확보 → Planner/Supervisor의 요건 검토·복구 → Composer의 근거 기반 답변 → 화면의 결과·근거 확인**으로 연결했다. 실제 Agent 호출은 질문에 필요한 조합을 순차 실행하며, 모든 질문에서 모든 Agent를 호출하지 않는다.

첫 4개 브랜치 통합 시 Python **647 passed**, 웹 **25 passed**를 기록했다. 후속 RAG 안정성 단계의 전체 Python 검사는 **661 passed, 기존 SQL 복구 회귀 1 failed**였고, PR #12 병합 커밋의 RAG 전용 재평가는 **149 passed**였다. 시점·범위가 다르므로 이를 더하거나 최신 전체 검사가 모두 통과한 것으로 표현하지 않는다.

원본 상세 비교·흐름도: [FAB Assistant As-Is → To-Be](adv_integrate_as_is_to_be.md).

# 현장 기록 조회 데이터 연결 기준

2026-09-13 현장 질문 재현에서 발견한 LOT/장비 식별자 소실, 집계 보고서 오선택,
작업 코드와 설비군 혼동, 계측 명칭 누락을 공통 조회 경로에서 개선한다.
문장별 SQL/답변을 등록하지 않고 실제 스키마와 업무 메타데이터로 조회한다.

## 데이터 추가 시 확인할 항목

| 업무 | 필요한 정보 | 확인할 의미 |
| --- | --- | --- |
| LOT 제한 이력 | LOT 키, 이벤트/제한 키, 설정·해제 시각, 설정자 키 | 해제·취소 포함 여부, 동시 제한 여러 건 처리 |
| 제한 사유 | 제한 키, 사유 코드·설명, 적용 기간 | 이벤트 설명과 공식 업무 사유의 차이 |
| 장비 상태·비가동 | 개별 장비 키, 상태·사유 코드, 발생·종료 시각 | 현재 상태 마스터 우선순위, 지연 이벤트 처리 |
| LOT 현재 상태 | LOT 키, 상태, 공정/단계, 관측 시각 | 마지막 이벤트와 현재 상태의 관계 |
| 자원 가용성 | 자원 키, 영역·그룹, 점유·예약, 사용 자격, 유효 시각 | 사용 가능한 빈 자원의 정확한 업무 조건 |
| 작업 코드 | 작업 코드·명칭, 영역, 활성 여부·유효 기간 | 설비군 또는 공정 step과의 관계 |
| 계측 매핑 | 매핑 키, 원공정·계측공정, 제품/경로/장비 범위, 유효 기간 | 중복 매핑, 우선순위, 폐기·비활성 포함 여부 |

마스킹한 키도 테이블 간 참조 일관성을 유지한다. 개인 이름을 가져올 수 없으면
마스킹 사용자 키까지만 제공하고 이름이 없음을 구분한다. 이벤트 발생 시각과
적재 시각, 타임존을 분리해서 설명한다.

## 기존 카탈로그 연결

`agent_meta.table_catalog`의 `description`, `aliases`, `relationships`, `semantics`에
업무 설명을 등록한다. 업무 담당자가 검토한 정의는 `semantics.managed_by=editor`로
설정하면 코드 기본값으로 덮어쓰지 않는다. 실제 컬럼 존재 여부는 매번 DB에서 확인한다.

- `grain`: 한 행이 나타내는 대상/이벤트/기간.
- `default_time_column`: 조회 기준 시각.
- `column_meanings`: 코드·상태·설정자·사유 각 필드의 의미.
- `entity_columns`: 비표준 키 이름을 쓰는 경우 `lot_id`, `equipment_id`,
  `resource_group`과 실제 컬럼의 대응. 예: `{"lot_id": "batch_key"}`.
- `facet_columns`: 업무 필드와 실제 컬럼의 대응. 예:
  `{"work_code": ["op_cd"], "setter": ["created_user_key"], "reason": ["hold_reason_cd"]}`.
  이벤트 종류·기록 역할·일반 설명을 공식 작업 코드·개인 설정자·업무 사유로 등록하지 않는다.
- `relationships`: 실제 조인 키, 대상, 관계의 개수 및 중복 처리 규칙.
- `notes`: 상태 우선순위, 가용성 조건, 데이터 최신성, 공식 기준 여부.

`entity_columns`는 출처 테이블의 실제 키를 지정한다. 비슷한 이름을 근거로
시뮬레이션 장비와 모델 설비군을 연결하는 데 사용하면 안 된다.

## 실행·답변 계약

1. 원문의 LOT/장비/그룹 ID를 보존하고 정확한 대상 필터가 있는지 SQL 실행 전에 검증한다.
2. 이력·사유·설정자·가용성·작업 코드·매핑은 단순 집계 템플릿의 대체 결과로 답하지 않는다.
3. 의미 계획의 `answer_coverage`가 요청 항목별 근거 컬럼과 available/partial/unavailable을 기록한다.
4. 개별 대상의 최신 기록은 대상 조건 안에서 찾는다. 과거 고장/제한 이벤트만 검색해서 현재 상태라고 단정하지 않는다.
5. 답변에는 확인된 기록을 먼저 제공하고 없는 항목을 구분한다. 역할은 개인 설정자, 이벤트 설명은 공식 사유와 동의어가 아니다.
6. `query_result.status`는 조회 실행 결과다. `answer_status`는 complete/partial/empty 또는 실패/미지원 상태를 구분하며 완전한 업무 정답의 보증은 아니다.
7. SQL 자체의 LIMIT과 실행기 반환 한도를 함께 반영한다. 한도에 도달한 행 수는 정확한 전체 건수로 안내하지 않는다.
8. 같은 구조의 제품별 경로 테이블은 `UNION ALL`로 합칠 수 있다. 각 출처의 필터를 유지하고 전체 결과에 정렬·한도를 적용한다. 집계·조인을 포함한 임의의 UNION 계획은 지원하지 않는다.
9. 업무 가용성 필드가 없으면 이벤트 상태에 임의의 `idle` 조건을 만들어 빈 자원이 없다고 결론 내리지 않는다. 최근 이벤트 조회와 자원의 실제 사용 가능 여부는 분리한다.

현재 지원은 메타데이터 기반 조회 계획과 검증을 확장한 것이다. 새 데이터의 업무 정의를
자동으로 확정하지 않는다. 특히 동시 제한의 활성 여부, 자격·예약을 포함한 가용성 조건,
공식 계측 매핑의 우선순위는 내일 추가할 데이터와 담당자 정의를 연결한 뒤 검증해야 한다.

## 신규 데이터 인수 검증

- 업무 담당자가 확인한 대상 ID와 기대 필드를 가진 기준 조회를 먼저 만든다.
- 정상/해제/비가동 아님/없는 ID/NULL 사유·설정자/여러 이력/늦게 적재된 이벤트 사례를 포함한다.
- 같은 업무 질문을 ID·표현·기간을 바꿔 실제 채팅 API로 실행한다.
- 기준 조회와 SQL의 대상·시간·결과를 비교한다. API 200이나 succeeded만으로 통과시키지 않는다.
- 공식 정보가 없는 항목은 데이터 부족 판정을 유지한다. 그럴듯한 대체값을 정답으로 채우지 않는다.

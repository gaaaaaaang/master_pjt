# 기본 질문 실행 경로 복구

작업 브랜치: `fix/adv_demo`.

## 원인과 변경

사용자 질문은 `FAB11 etch 공정의 대기 시간이 늘어난 원인을 근거로 분석해 줘`였다.
실행 중인 API 서버와 같은 작업 경로의 설정을 확인했을 때 Docker와 로컬 PostgreSQL이 중단되어 있었다.
DB 연결 실패가 Text2SQL의 초기 카탈로그 조회에서 발생하면 빈 딕셔너리가 남았고,
후속 코드가 이를 정상적으로 조회한 빈 카탈로그로 해석해 질문을 `unsupported`로 반환했다.
이 때문에 실제 연결 장애가 “지원 table catalog에 매핑되는 대상이 없습니다”로 보였다.

- 기존 DB 볼륨을 유지해 PostgreSQL을 다시 시작했다. FAB10~13의 스냅샷 테이블을 확인했다.
- 카탈로그 조회 오류는 `failed`와 DB 연결 안내로 반환한다. 여러 FAB 중 일부만 조회한
  카탈로그도 정상 결과로 사용하지 않는다. 연결 문자열과 내부 오류는 답변에 노출하지 않는다.
- `/health`는 기존 서버 생존 확인 용도를 유지한다. `/health/ready`는 읽기 전용으로
  FAB10~13 스냅샷 테이블과 적재 여부를 확인하며, 장애·미적재는 503으로 구분한다.
- 화면은 30초마다 준비 상태를 확인한다. DB가 중단되어도 “서버 연결 완료”로만 보이던
  표시를 데이터 연결·적재 상태 안내로 바꿨다.
- PostgreSQL에 `restart: unless-stopped`를 설정했다. Docker 자체가 실행되어 있어야 한다.

## 사용자 요청에 따른 fallback 제거

사용자는 케이스별 하드코딩과 정해진 답변으로 덮어쓰는 fallback을 명시적으로 금지했다.
이번 작업 중 추가했던 날짜·표현별 검증 예외도 철회했다. 특정 실패 문장을
통과시키는 새 정규식은 추가하지 않았다. 아래 공통 의미 검토 계약을 적용했다.

다음 기존 경로를 제거했다.

- Planner 모델 장애 시 키워드로 계획을 대신 만드는 함수와 다중 FAB의 모델 계획 우회.
- Composer 모델 장애 시 질문 범위·조회 행·제한 문장을 붙여 답변을 만드는 경로.
- FAB 비교용 정해진 답변 조립 함수와 검토 실패 시 그 답변으로 자동 교체하는 경로.
- 후처리에서 단일 행의 WIP·온도 등을 정해진 문장으로 바꾸는 경로.
- 출처 문구를 정규식으로 지워 답변을 다시 쓰는 후처리와 사용되지 않는 mock 답변 모듈.
- 검토 모델이 실패했을 때 모델 검토 없이 자동 승인하거나 계속 진행하는 경로.

현재 최종 분석 문장은 Composer 또는 검토 모델이 작성한다. 수정이 필요하면 같은
근거와 검증 조건으로 최대 세 번의 모델 검토를 수행하며, 끝까지 검증되지 않으면 실패로
표시한다. 준비된 정답 문장이나 임의의 조회 결과로 바꾸지 않는다. 모델 호출 실패도
실행 오류로 전파한다. 일반 오류 안내, 읽기 전용 SQL 검증, 지표 정의·집계 계산,
문서 검색 순위 계산은 답변 대체 함수가 아니므로 유지한다.

Composer와 검토 프롬프트를 공통 근거 계약 중심으로 정리했다. 질문의 전제, 관측값,
기간과 단위, 원인 후보와 확정 원인, 조건부 계산, 실제로 없는 근거를 구분하도록 했다.
중복 표·반복 경고·내부 키 나열을 줄이고, 상대 기간과 정확한 날짜 및 제공된 요약값을
사용하도록 지시한다. 다중 FAB도 모델이 실제 실행 계획을 작성한다.

## 검증 방식

이 문서에 언급한 원시 JSON 실행 기록과 DB 캡처는 로컬 진단 자료이며 PR에는 포함하지 않는다.
PR에는 재현용 스크립트·시험과 아래 검증 결과 및 미완료 범위를 포함한다.

화면과 검증 스크립트가 `apps/web/src/default-questions.json`을 공유한다.
생산 현황·원인 찾기·추이 비교 각각 FAB10~13, FAB 지정이 필요 없는 공정 지식 1개로
총 13개 조합을 실제 `http://127.0.0.1:8000/api/chat/stream`에 요청한다.
모델은 사용자 승인을 받은 현재 설정의 `skax.ai-talentlab.com` API를 사용한다.

통과 조건에는 응답 성공, 실모델 호출·답변 작성, 최종 답변 검토 승인, FAB/공정/지표,
조회 행 수, 차트 또는 문서 근거가 포함된다. 원인 찾기는 최소 두 시점의 관측값과 문서
근거를 요구한다. 각 요청은 새 대화이며 모델 요청 사이에 25초 간격을 둔다.
기존 보고서는 덮어쓰지 않는다. 최종 실행에서는 소스 해시가 도중에 바뀌면 전체 실패로 판정한다.
동일 사용자 질문의 별도 실제 HTTP 실행은 `no_fallback_user_exact.json`에 기록했다.

첫 탐색 실행은 10/13이었다. FAB13 원인 찾기, FAB10·FAB11 추이 비교가 조회 후 문장
검증에서 막혔다. 실행 도중 개선을 적용한 탐색 기록이므로 엄밀한 성능 기준선으로 쓰지 않는다.
원문과 수정 제안, 실패 사유는 `defaults_round1.json`에 남겼다.
사용자 요청 전 실행하던 재시험은 `defaults_interrupted_before_fallback_removal.json`으로
남기고 중단했다. fallback 제거 후 전체 실행은 `no_fallback_defaults.json`, 원본 DB를 별도로 집계한 수치 대조는
`numeric_audit.json`에 기록한다. 모든 자료는 `apps/assistant/output/evals/defaults_20260913/`에 있다.

원본 대조는 모델이 만든 SQL을 재실행하지 않는다. 캡처한 원본 스냅샷을 Python Decimal로
집계해 12개 데이터 질문의 행·공정·평균·합계를 비교한다. 이는 반환 데이터의 검증이며
모든 자연어 문장의 정확성을 보장하는 지표와는 구분한다.

## 재실행

저장소 루트에서 실행한다. API와 웹은 기존 개발 실행 방식으로 기동한다.

```sh
docker compose up -d postgres
curl -s http://127.0.0.1:8000/health/ready
PYTHONPATH=apps/assistant/src:apps/assistant/scripts .venv/bin/python apps/assistant/scripts/evaluate_default_questions_http.py --live --output /tmp/defaults-new.json
PYTHONPATH=apps/assistant/src:apps/assistant/scripts .venv/bin/python apps/assistant/scripts/audit_default_questions.py --report /tmp/defaults-new.json --capture --reference /tmp/defaults-reference-new.json --output /tmp/defaults-audit-new.json
```

## 해석 범위

대기 시간이 늘었다는 질문의 전제는 조회 결과로 먼저 확인해야 한다. 전체 기간에 감소가
관측되면 이를 그대로 답하고, 문서의 후보 원인과 해당 FAB의 확정 원인을 구분한다.
이번 변경은 없는 사건이나 증가 수치를 만들어 질문에 맞추는 방식이 아니다.
한 번의 실모델 통과율은 서비스의 장기 성공률을 의미하지 않는다. 반복되는 출처 문구나
7일의 관측 창과 8개 날짜 집계의 표현 혼동 등 자연어 품질은 수동 검토도 필요하다.

## 로컬 시험의 의미

모델 장애 시 대체 답변을 기대하던 시험은 오류 전파와 답변 미생성을 확인하도록 변경했다.
계획의 범위·의존성 시험은 성공한 모델 응답 fixture를 명시적으로 주입한다. 검토 수정의
작성 주체와 재검증, 최대 시도 수, 후처리가 모델 답변을 보존하는 것도 확인한다.

기존 오프라인 품질 평가가 fallback 계획을 Planner 정확도로 집계하던 부분은 제거했다.
기준선 버전 74의 `adversarial.planner_outage_propagation_pass_rate`는 장애 전파 시험이다.
Planner의 실제 모델 정확도와 구분하며, 실제 동작은 별도의 HTTP 실모델 실행으로 확인한다.

## 추가 제거 감사

문서 답변에서 버전 관리 질문을 정규식으로 판별해 특정 문장을 덧붙이던 처리와,
승인·기록 질문에 원문 문장을 자동으로 추가하던 `retain_procedural_requirements`를 삭제했다.
문서의 주장별 근거와 요청 항목 충족 여부는 기존 공통 모델 검토로 판단한다.
검토가 누락을 지적하면 partial로 남기며 코드가 답변을 완성하지 않는다.

Text2SQL의 `_execute_empty_result_repairs`와 후보 SQL 생성 함수들도 삭제했다.
빈 결과 또는 실행 오류 뒤 기간·상대값·제품·장비 조건을 치환하거나, exact 조건을
부분 일치로 넓히거나, 미리 작성한 PM JOIN으로 재조회하던 경로가 대상이다.
모델 SQL을 실행 직전에 정규식으로 수정하던 `_normalize_operational_sql`도 삭제했다.
공통 Text2SQL 프롬프트에서 실제 카탈로그의 값·컬럼 의미를 확인하고, 실행 피드백을
받아도 명시한 범위를 넓히지 않도록 했다. 구조화된 지표 정의와 정상 집계 SQL은 유지한다.

`no_fallback_defaults.json`은 이 추가 삭제 이전의 고정 소스에서 13/13 통과했다.
동일 결과의 독립 원본 집계 대조도 12/12 통과했으며
`numeric_audit_before_final_removal.json`에 기록했다.
추가 삭제 이후의 재시험은 `final_defaults.json`에 별도로 기록한다.

## 검색 평가에서 남은 차이

현재 사용 중인 확장 코퍼스 `master_pjt_final_adv.jsonl`의 검색 평가는 Recall@3 1.0,
MRR 0.9667이다. `basics_critical_queue_time`에서 일반 용어 설명이 1위,
SMT2020 원문 구현 설명이 2위다. 따라서 MRR 1.0을 요구하는 기존 오프라인 릴리스
기준은 통과하지 못했다. 이번에 검색 코드를 수정하지 않았으며, 기존 v2 코퍼스를
대상으로 같은 평가를 실행하면 MRR 1.0이다. 기준이나 정답 ID를 낮춰 통과시키지 않았다.
이는 기본 질문의 실제 성공 여부와 별도로 남기는 검색 순위 개선 과제다.

## 문장 의미 검토 계약

추가 반복 시험에서 FAB11의 유효한 ‘후보 원인’ 표현도 기존 어휘 검사에 거절되었다.
실패 기록은 `defaults_before_semantic_review.json`에 보존하고 실행을 중단했다.
표현별 예외 추가 대신 `verify_response`의 진단·출처·조건 관련 자연어 탐지 결과를
`semantic_warnings`로 분리하고, 구조·수치 검증 결과를 `blocking_warnings`로 구분했다.
기존 어휘 기반 진단 결과는 감사용 `warnings`에도 그대로 남는다.

최종 검토 모델은 각 의미 검사 항목에 `warning_index`, `violated`, `reason`을 반드시
작성해야 한다. 누락·중복·실제 위반은 승인할 수 없다. 단순히 모델이 approved=true라고
해도 이 계약과 수치 검사를 통과해야 한다. 모델이 수정한 문장에도 동일한 검사를 적용하며,
의미 검토가 남아 있으면 다음 모델 검토를 받는다. 모델 장애 시 자동 승인은 없다.

공통 프롬프트에는 시작·끝 값의 감소와 중간 구간의 증가가 공존할 수 있음을 명시했다.
관측값을 지우거나 증가 사실 전체가 없다고 과도하게 단정하지 않도록 한 일반 시계열 원칙이다.
오프라인 어휘 평가 점수는 모델의 의미 판단 정확도와 같지 않으며 실모델 시험과 구분한다.

### 검토 입력의 오탐 유도 제거

표현 검사 결과를 ‘위반’ 문장으로 전달하면 모델이 이를 그대로 따라가는 문제가 FAB12
재시험에서 관측되었다. `defaults_semantic_probe_bias.json`에 원문과 수정 시도들을 남겼다.
최종 수정에서는 모델 입력에 강제 가능한 수치·구조 경고와 중립적인 검토 주제만 전달한다.
어휘 검사 원문, 합산 품질 점수, 어휘 기반 is_supported 판정은 모델 입력에서 제외하고
감사 기록에만 남긴다. 각 주제의 실제 위반 여부는 여전히 모델이 명시적으로 판단해야 한다.

SQL 수치가 확보되었으면 해당 관측값은 답변 가능하며, 원인·문서 근거 부족이 관측값 자체를
무효화하지 않는다는 기준을 Composer와 검토 프롬프트에 공통으로 명시했다.
최종 로컬 시험은 백엔드 956개 통과, 수정 파일 Ruff 및 diff 검사 통과다.
웹 시험 37개와 빌드도 통과했고 실제 화면에서 준비 완료 표시를 확인했다.

최종 중립 입력 변경 뒤에는 과거 답변·검토 기록을 재사용한 실모델 재시험을 시도했으나,
자동 승인 검토가 파생 기록의 외부 재전송을 별도 승인이 없는 작업으로 거절했다.
이 재시험은 실행되지 않았으며 사용자에게 추가 승인을 요청한 상태다.
따라서 현재 최종 소스에 대한 기본 질문 전체·연속 대화 실모델 검증은 완료로 표시하지 않는다.
`final_defaults.json` 최종 보고서는 아직 없다. 앞선 실행의 통과 수치와 혼동하지 않아야 한다.

**시나리오 1 :&#x20;****현재 상태 조회 시나리오**

* ID : [SC-001]

* 상황 : 사용자가 특정 라인이나 공정의 현재 상태를 빠르게 확인해야할 때. (예. 지금 A라인에 WIP 몇 개야? 와 같이 즉시 수치가 필요한 경우)

* 목표 : 원하는 라인/공정의 현재 현황을 정확하게 조회

* 사전 조건

  * 생산 데이터가 db에 적재되어 있어야 한다.

  * 사용자는 조회 대상 라인명이나 공정명을 입력할 수 있어야 한다

* 상세 흐름

|    |                                                     |                                                                                                  |            |
| -- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ---------- |
| 단계 | 사용자 행동                                              | 시스템 동작                                                                                           | 비고         |
| 1  | "지금 M10 A라인 WIP 몇개야?" 질문 입력                         | 질문에서 메타 정보(FAB 정보 : M10, 라인 : A라인,,,)를 식별한다                                                      | 자연어 입력     |
| 2  | 질의를 planner가 분류                                     | 질의에 답하기 위한 세부 task를 나눠 답변에 필요한 행동 계획을 세움                                                         | 세부 task 계획 |
| 3  | supervisor가 "현재 상태 조회"가 적절하다 판단 후 text2sql agent 호출 | - planner가 세운 계획을 보고 가장 적합한 sub-agent 판단 - 재질문 여부를 판단하고, 충분하다 판단하면 planner 결과와 일치하는 sub-agent 호출 | 분기 판단      |
| 4  | text2sql이 SQL 생성한다                                  | 최근 추이, 전일/전주 비교, 이상 발생 시점, 관련 공정별 수치 등을 조회할 수 있도록 쿼리를 생성한다                                       | 쿼리 생성      |
| 5  | 답변 생성 agent가 최종 응답 생성                               | 답변 생성 agent가 sql 결과를 바탕으로 사용자가 이해할 수 있는 자연어 답변 생성                                                | 답변 생성      |
| 6  | supervisor가 생성된 sql 결과와 답변의 적합성을 판단                 | 사용자 의도에 맞는 답변이 생성되었는지 판단 (육하원칙에 맞게) * 의도와 다른 답변 생성했을 때 3단계로 돌아감                                  | 검증 단계      |
| 7  | Agent 답변을 확인하고 사용자가 피드백 입력                          | 사용자 피드백을 바탕으로 self-reflection으로 사용 *(질문&sub-agent 답변&최종 답변&사용자 피드백 쌍으로 데이터 저장)*                  | 셀프 검증 단계   |

* 입력 예시

```text
지금 M2라인 WIP 몇 개야?
```

* 기대 출력

```text
M2라인의 현재 WIP는 128개입니다.
기준 시각: 2026-08-24 14:10 KST
```

* 성공 기준

  * 기준 1: planner가 사용자 질의를 보고 알맞은 세부 task 계획

  * 기준 2: supervisor가 planner결과를 보고 적절한 sub-agent 판단

  * 기준 3: sub-agent가 적절한 답변 생성

**시나리오 2 :****&#x20;원인 진단형**

* ID : [SC-002]

* 상황 : 사용자가 특정 라인/공정의 지표가 왜 나빠졌는지 원인을 확인해야 할 때.\
  (예. 왜 A라인 Queue Time이 늘었어? / 왜 M10 공정의 WIP가 증가했어? 와 같이 현황 조회가 아니라 원인 분석이 필요한 경우)

* 목표 : 실제 공정 데이터와 공정 기본 지식을 활용해 지표 악화의 원인을 설명한다

* 사전 조건

  * 공정 데이터가 db에 적재 되어야한다

  * 공정 문서, 운영 기준과 같은 지식 문서가 vDB에 적재 되어야한다

  * 사용자는 답변에 필요한 메타 데이터(fab 정보, 라인명, 공정명,,,)를 입력해야한다

* 상세 흐름

|    |                                                     |                                                                                                   |            |
| -- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ---------- |
| 단계 | 사용자 행동                                              | 시스템 동작                                                                                            | 비고         |
| 1  | "왜 A라인 Queue Time이 늘었어?" 질문 입력                      | 질문에서 메타 정보(FAB 정보 : M10, 라인 : A라인,,,)를 식별한다                                                       | 자연어 입력     |
| 2  | 질의를 planner가 분류                                     | 질의에 답하기 위한 세부 task를 나눠 답변에 필요한 행동 계획을 세움                                                          | 세부 task 계획 |
| 3  | supervisor가 "원인 진단"가 적절하다 판단해 text2sql,rag agent 호출 | - planner가 세운 계획을 보고 가장 적합한 행동 판단 후 sub-agent 조합 호출 - 재질문 여부를 판단하고, 충분하다 판단하면 적절한 sub-agent 조합 호출 | 분기 판단      |
| 4  | text2sql agent가 SQL 생성                              | 최근 추이, 전일/전주 비교, 이상 발생 시점, 관련 공정별 수치 등을 조회할 수 있도록 쿼리를 생성                                          | 쿼리 생성      |
| 5  | RAG로 공정 지식 검색                                       | Queue Time 증가, WIP 증가, 병목, 다운타임 등과 관련된 공정 문서와 운영 지식을 검색한다.                                        | 지식 검색      |
| 6  | text2sql 결과와 RAG 결과를 결합                             | DB에서 확인한 수치 변화와 공정 지식의 원인 후보를 함께 정리한다.                                                            | 조합 단계      |
| 7  | 답변 생성 agent가 최종 응답 생성                               | 수치 근거와 문서 근거를 결합해 가능한 원인, 영향 지점, 추가 확인 포인트를 자연어로 정리                                               | 답변 생성      |
| 8  | supervisor가 최종 답변의 적합성을 판단                          | 사용자 의도에 맞는지, DB 근거와 공정 지식이 함께 반영되었는지 검토                                                           | 검증 단계      |
| 9  | Agent 답변을 확인하고 사용자가 피드백 입력                          | 사용자 피드백을 바탕으로 self-reflection에 활용한다.                                                              | 셀프 검증 단계   |

* 입력 예시

```text
왜 A라인 Queue Time이 늘었어?
```

* 기대 출력

```text
A라인의 Queue Time 증가는 최근 3일간 특정 공정 앞 대기 건수가 증가한 것과 연관됩니다.

DB 확인 결과:
- 전일 대비 Queue Time: 18% 증가
- 동일 시간대 WIP: 12% 증가
- 병목 공정: A2 공정

공정 문서 기반 확인 결과:
- Queue Time 증가는 병목 공정의 처리량 저하 시 자주 발생
- 상류 공정 투입량 증가 시 대기 적체가 발생할 수 있음
- 설비 다운타임이나 작업자 교대 이력도 영향 요인으로 확인됨

가능한 원인:
1. A2 공정의 처리 속도 저하
2. 상류 공정 투입 증가로 인한 대기 적체
3. 설비 가동률 변동 또는 작업자 교대 영향

추가 확인 포인트:
- A2 공정의 설비 다운타임
- 작업자 교대 이력
- 직전 공정 투입량 변화
```

* 성공 기준

  * 기준 1: planner가 사용자 질의를 보고 알맞은 세부 task 계획

  * 기준 2: supervisor가 planner결과를 보고 적절한 sub-agent 조합 판단

  * 기준 3: sub-agent가 적절한 답변 생성

**시나리오 3 :&#x20;****영향도 질의 시나리오**

* ID : [SC-003]

* 상황 : 사용자가 특정 공정 지연, 설비 이슈, 수율 변화 등이 전체 생산 지표에 얼마나 영향을 주는지 확인해야 할 때.\
  *(예. "이 공정 지연이 이번주 수율에 얼마나 영향을 줘?" 와 같이 변화의 영향 크기를 정량적으로 알고 싶은 경우)*

* 목표 : 특정 이벤트나 공정 변화가 수율, 리드타임, WIP 등 핵심 지표에 미치는 영향을 수치로 계산하고, 수치를 바탕으로 영향도를 산정해 답변 제공

* 사전 조건

  * 생산 데이터가 db에 적재되어 있어야 한다.

  * 영향도 계산에 필요한 기준 지표, 비교 기간, 대상 공정/라인 정보 등 메타 데이터를 질문에서 식별 가능해야 한다.

  * 영향도 계산 결과를 해석할 수 있는 기준 문구 또는 해석 규칙이 준비되어 있어야 한다.

  * 사용자는 영향 대상과 기간을 질문할 수 있어야 한다.

* 상세 흐름

|    |                                     |                                                                |            |
| -- | ----------------------------------- | -------------------------------------------------------------- | ---------- |
| 단계 | 사용자 행동                              | 시스템 동작                                                         | 비고         |
| 1  | "이 공정 지연이 이번주 수율에 얼마나 영향을 줘?" 질문 입력 | 질문에서 메타 정보(FAB 정보, 공정, 영향 대상 지표, 기간)를 식별한다.                    | 자연어 입력     |
| 2  | 질의를 planner가 분류                     | 질의에 답하기 위한 세부 task를 나눠 답변에 필요한 행동 계획을 세움                       | 세부 task 계획 |
| 3  | supervisor가 "영향도 질의"로 판단            | planner가 세운 계획을 검토해 적절한 sub-agent 조합을 판단하고, 필요 시 재질문 여부를 결정한다. | 분기 판단      |
| 4  | 영향도 계산 tool이 수치 계산 수행               | 공정 현황 테이블을 불러와(text2sql로 추가 쿼리 생성 x) 영향도 수치 계산                 | 수치 계산      |
| 5  | 영향도 해석 agent가 계산 결과 해석              | 계산된 수치를 사용자가 이해할 수 있는 표현으로 바꾸고 의미와 해석 포인트를 정리한다.               | 수치 기반 해석   |
| 6  | supervisor가 계산 결과와 해석의 적합성을 판단      | 계산식, 기준값, 해석 문장이 질문 의도와 맞는지 검증한다.                              | 검증 단계      |
| 7  | Agent 답변을 확인하고 사용자가 피드백 입력          | 사용자 피드백을 바탕으로 self-reflection에 활용한다.                           |            |

* 입력 예시

```text
이 공정 지연이 이번주 수율에 얼마나 영향을 줘?
```

* 기대 출력

```text
이번주 해당 공정 지연으로 인해 수율은 약 1.8%p 하락한 것으로 추정됩니다.

확인된 영향:
- 기준 대비 불량 증가 기여도: 62%
- 지연 공정 관련 재작업 증가: 14%
- 최종 수율 손실 추정치: 1.8%p

- 지연이 발생한 시점 이후 불량률과 재작업률이 함께 상승했습니다.
- 영향은 주로 해당 공정의 처리 지연과 후속 공정 적체에서 발생한 것으로 보입니다.

추가 확인 포인트:
- 지연 발생 시점의 설비 가동률
- 해당 공정의 투입량 변화
- 후속 공정 대기 시간 변화
```

* 성공 기준

  * 기준 1: planner가 사용자 질의를 보고 알맞은 세부 task 계획

  * 기준 3: sub-agent가 적절한 답변 생성

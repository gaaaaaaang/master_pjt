# RAG 안정성 개선과 변동 원인 분석

`feat/rag_adv2`의 `5bd7d03`을 기준으로 후속 수정했다. 결론은 **상태 판정은 이번
동일 코드 반복에서 이미 일관됐고, 수정 호출·분량·시간의 변동을 줄일 여지가 있었다**는
것이다. 또한 관련성 점수의 급락 일부는 실제 검색 실패가 아니라 평가 지표의 0점 처리에서
발생했다. RAG 전체가 안정화됐다는 결론은 아직 내릴 수 없다.

## 왜 이전 결과가 달랐나

### 1. 이전 표는 같은 코드의 반복 실험이 아니었다

앞선 v5, v6, v7은 버전 관리 검증과 생성 오류 수정 경로가 서로 다른 코드다.
v5의 높은 관련성에는 문서 상태를 버전 관리 기준으로 오해한 답변도 포함된다.
v6는 그 답변을 정상적으로 partial로 낮췄다. 따라서 0.5157 → 0.3084 → 0.4640을
전부 같은 코드의 난수 변동으로 해석할 수 없다.

이번에는 기준 코드와 수정 코드를 각각 고정하고, **같은 질문·같은 검색 근거로
각각 3회씩** 생성·검토만 호출했다. 6문항 × 3회 × 전후 2개 = 36회다.
서로 다른 코드의 개선 효과와 동일 코드 안에서의 반복 변동을 구분했다.

### 2. 생성과 내부 검토의 sampling 설정이 명시되지 않았다

기존 `AzureAgentClient`의 요청 payload에는 temperature가 없었다. 서버 기본값을
사용한 것은 확인되지만 실제 기본값이 몇인지는 이번 실험으로 확인하지 않았다.
RAG 생성과 검토만 `temperature=0.0`을 명시하도록 변경했다. 다른 에이전트는 기존
동작을 유지한다. 실제 호출 기록에서도 기준은 null(미지정), 변경 후는 0.0임을 확인했다.

temperature 0은 완전한 재현성을 보장하지 않는다. 변경 후에도 대체 장비 질문의
답변이 1,208/699/620자로 달랐다. 샘플링과 프롬프트를 함께 수정했으므로 각각의
인과 효과를 따로 측정했다고 주장할 수 없다.

### 3. 답변 범위와 검토 기준이 넓어질 수 있었다

검색 근거에는 특정 절차와 일반 RACI·복구 설명이 함께 들어간다. 생성 모델이 일반
역할·배경까지 덧붙이면 주장 수와 인용 수가 늘고, 검토할 조건도 많아진다.
이전 PM 실행에서는 명시적인 Engineer 승인 조건을 다른 manager 승인 문구와 충돌한다고
판단해 제외한 검토 오류가 있었다. 모델 검토 자체도 완전한 정답 판정기가 아니다.

이번에는 질문의 역할·의사결정별로 간결하게 작성하고 한국어 원문은 조건을 보존하면서
원문 표현을 우선하도록 했다. 검토에는 **질문에서 요구사항을 도출**하고, 생성한 추가
배경에서 새로운 요구사항을 만들지 않도록 명시했다. 사실의 근거성과 질문의 완전성을
분리하며, 복수 승인 조건은 원문에 대체 관계가 명시되지 않으면 충돌로 보지 않도록 했다.
이것은 모델 지시 보완이며 일반적인 의미 검증 보장은 아니다.

### 4. Ragas 관련성에는 0으로 떨어지는 판정이 있다

설치된 Ragas 0.2.15의 `ResponseRelevancy` 구현을 확인했다. 기본 strictness=3으로
답변에서 질문 3개를 생성하고, 원 질문과의 embedding cosine similarity를 평균한다.
이때 **3개 중 하나라도 noncommittal이면 평균 유사도에 0을 곱한다.**

고정된 최종 v7 답변 2개를 각각 3번 다시 채점하고 실제 생성 질문과 판정을 기록했다.
문서 근거를 숨기거나 한계 문장을 삭제해 점수를 높이는 방식은 사용하지 않았다.

| 같은 답변을 반복 채점 | 평균 유사도 | noncommittal | 최종 관련성 |
|---|---|---|---|
| PM 승인 답변 3회 | 0.5024 / 0.4976 / 0.4976 | 매회 0,0,0 | 유사도 그대로 |
| KB 부분 답변 3회 | 0.5868 / 0.5852 / 0.5876 | 매회 1,1,1 | 매회 0 |

KB 문서에는 업데이트 기준은 있지만 버전 관리 기준은 없다. 정상적인 부분 답변과
그 한계 설명 때문에 지표가 0이 되는 현상을 이번 재채점에서 직접 확인했다.
이 사례의 0은 “질문과 전혀 무관함”이나 “검색 실패”와 같지 않다. 이전 각 실행의
채점 내부 응답은 보존되지 않았으므로 과거 모든 0점을 이 원인으로 확정하지 않는다.

### 5. 구조·숫자 검증 실패와 답변 품질 저하는 별개다

이번 기준 코드에서 없는 재가동 시간 질문은 3번 모두 `insufficient`이면서 claims를
동시에 생성했다. 기존 1회 수정 기능 덕분에 최종 답변은 정상 보류했지만 매번 추가
호출이 필요했다. 변경 후는 3번 모두 첫 생성부터 빈 claims로 정상 보류했다.
이전 Hold 실행의 숫자 검증 실패도 원문 일치 검증이 작동한 사례다. 단, 당시 원시
생성 결과가 없어 어떤 숫자를 왜 생성했는지까지는 확정하지 않는다.

재현 스크립트는 이제 생성·수정·검토 입력과 출력을 모두 보존한다. 최종 status만
비교하다가 내부 실패나 검토 오판을 놓치는 문제를 줄였다.

## 전후 반복 실험 결과

사용한 6문항은 PM 승인, Hold 비교, 장비 정지 역할, 대체 장비, KB 업데이트,
없는 재가동 시간이다. 기존 corpus의 동일 근거를 고정했으므로 검색 및 HTTP/SSE
안정성 측정은 아니다. 개발 사례를 사용한 소규모 회귀이며 독립 holdout은 아니다.

| 측정 | 기준 5bd7d03 | 변경 후 |
|---|---:|---:|
| 반복 간 상태 일치 문항 | 6/6 | 6/6 |
| 검증 오류 후 수정이 필요했던 실행 | 3/18 | 0/18 |
| 최종 검증 거절 | 0/18 | 0/18 |
| 모델 호출 수 | 36 | 33 |
| 평균 생성·검토 시간 | 8.73초 | 6.16초 |
| 평균 최종 답변 길이(인용 포함) | 805자 | 608자 |
| 문항별 길이 변동계수의 평균 | 9.34% | 5.71% |

길이 변동계수는 문항별 3개 길이의 population 표준편차 / 평균이고, 이를 6문항에서
평균했다. **내용 정확도나 의미적 안정성 지표가 아니다.** 짧아졌다고 더 정확하다고
단정하지 않는다. 호출은 기준 후 변경 순서로 실행됐으며 서버 부하를 통제하지 않았다.
시간 감소 전부를 코드 효과로 볼 수 없다. 양쪽의 인용은 모두 제공 원문과 일치했다.

변경 후 PM 3회는 Engineer 승인, manager 승인·low risk·risk memo, PM 이후 결과
기록을 모두 표시했다. Hold 비교의 보류·해제 조건도 유지했다. 최종 상태는 양쪽 모두
일반 답변 12회 supported, KB 3회 partial, 없는 수치 3회 insufficient였다.
상태 일관성이 변경 전보다 높아졌다고 주장하지 않는다.

대체 장비 질문의 길이 변동계수는 **18.75% → 30.93%로 악화**됐다. 초기 생성 주장도
변경 후 7/3/4개로 달랐다. 여러 복구 절차를 함께 쓰는 질문은 temperature와 지시만으로
범위가 안정화되지 않았다. 문항별 상세값과 모든 원문은 아래 JSON에 보존했다.

## 검증과 다음 우선순위

- 전체 Python 661 passed, 기존 SQL 복구 테스트 1 failed. 해당 실패는 앞선 기준
  `4ebf833` 검사에서 재현했던 동일한 실패다. 변경 파일 Ruff와 diff 검사 통과.
- RAG만 temperature를 명시하는 payload 검사, 다른 client의 미지정 동작 유지,
  실제 문서 생성 경로의 0.0 선택을 테스트했다.
- 이번 변경의 Ragas 전체 10문항 수치를 새로 산출하지 않았다. 이전 0.9714/0.4640을
  새 코드의 성능인 것처럼 재사용하지 않는다. 이번 외부 검증은 36회 고정 근거 생성과
  고정 답변 6회 관련성 성분 재채점이다.
- 다음 우선순위는 대체 장비 같은 복합 절차에서 질문 요구사항과 인용할 근거를 먼저
  고정하는 구조화된 답변 계획이다. 일반 복구·RACI 문서가 답변 범위를 넓히는 사례를
  검증셋으로 삼고, 빠진 조건 없이 안정적으로 범위를 줄이는지 확인해야 한다.
- 성공/부분/보류의 적절성, 질문별 필수 조건 누락, 원문 의미 왜곡을 별도 평가해야 한다.
  Ragas 관련성 하나를 최적화하거나 보류 문구를 없애는 방식은 적합하지 않다.
